# Team Workflow

How we branch, review and merge, and what the automated checks do.

For installing and running the project, see rust-godot-setup.md.

## Rules

- Don't commit straight to main. Everything goes through a branch and a pull request.
- main should always build and run, so anyone can clone it and demo the game.
- One branch per user story, matching a Trello card.
- Keep branches short lived. Days, not weeks. Long branches mean bad conflicts.
- Say something in the group chat before editing a shared scene. `.tscn` files merge badly, see the conflicts section.

## Branch names

Use the Trello card number so you can tell what a branch is for:

```
feature/52-starter-deck
feature/2-draw-randomised-hand
fix/34-energy-not-resetting
docs/update-setup-guide
chore/add-ci
```

The prefixes we use:

- `feature/` for a user story off the board
- `fix/` for a bug in something already merged
- `docs/` for documentation only
- `chore/` for tooling, CI or config, nothing that changes gameplay

So `<prefix>/<card-number>-<short-description>`. Leave the number out if there's no card for it, like docs or chore work.

## Starting work

Branch off an up to date main:

```bash
git checkout main
git pull

git checkout -b feature/52-starter-deck
```

Then commit in small chunks as you go instead of one huge commit at the end:

```bash
git add cyber_heist/src/deck.rs
git commit -m "Add Deck::draw with reshuffle on empty draw pile"
git push -u origin feature/52-starter-deck
```

Push early, even if the work isn't finished. It backs it up and lets everyone see what's in progress.

Write commit messages that say what the change does, like "Add energy reset at turn start". Not "stuff" or "fixes".

## Keeping your branch up to date

If your branch is going to be around for more than a day or two, pull main into it regularly. Sorting out a few small conflicts as you go is much easier than a pile of them at the end.

```bash
git checkout main
git pull
git checkout feature/52-starter-deck
git merge main
# fix any conflicts, then
cd cyber_heist
cargo build && cargo test
git push
```

## Pull requests

Open a PR from your branch into main. In the description:

- link the Trello card
- say what you changed in a sentence or two
- mention anything the reviewer needs to check by hand, especially anything you can only see in the Godot editor, since CI can't check that

Then request a review from someone else on the team.

## Review and merging

Our Definition of Done says work has to be peer reviewed by someone else, so don't merge your own PR.

If you're reviewing, check that:

- CI is green
- the acceptance tests on the Trello card actually pass
- there are unit tests for the new logic, including edge cases
- anything non obvious is commented
- you pulled the branch and ran it in Godot, if it changes something you can see

Use Squash and merge. That turns the branch into one commit on main, so our history is one commit per user story instead of forty "wip" commits. Delete the branch after, GitHub gives you a button for it.

Then clean up locally:

```bash
git checkout main
git pull
git branch -d feature/52-starter-deck
```

## Conflicts

Most of our conflicts won't be in Rust code. Watch out for these.

Scene files (`.tscn`, `.tres`) are the worst one. They're text, but Godot rewrites node and resource IDs all through the file when you edit a scene. If two people edit the same scene the conflict is genuinely hard to fix by hand, and getting it wrong gives you a broken scene rather than an error. Agree who owns a scene before editing it. Lots of small scenes are much easier to live with than one big one.

`project.godot` gets rewritten by the editor whenever you change project settings. The conflicts are usually easy but read them properly, otherwise you can quietly delete someone's setting.

`Cargo.lock` conflicts when two branches add dependencies. Don't edit it by hand, take main's version and regenerate it:

```bash
git checkout --theirs cyber_heist/Cargo.lock
cd cyber_heist && cargo build
```

`.uid` files are generated by Godot next to scripts and extensions. We commit them on purpose and they're stable, so they shouldn't normally conflict.

`.godot/` and `target/` are gitignored. If you see them in a diff something's wrong with the ignore rules, don't commit them.

## CI

The config is in `.github/workflows/ci.yml`. On every push to main and every pull request, GitHub starts a clean Ubuntu machine and runs:

```bash
cargo fmt --all -- --check
cargo clippy --all-targets -- -D warnings
cargo build
cargo test
```

The PR then shows a green tick or a red cross. The point of it running on a clean machine is that code can build on your laptop because of something only you have installed, and CI catches that straight away instead of the night before a demo.

That covers code formatting and linting as well as two things from our Definition of Done: no compiler errors, and passing unit tests.

What it can't check is anything to do with Godot. It doesn't install the engine, so it never opens the editor or runs the game. A PR can be completely green and still fail to load as an extension or look wrong on screen. Anything visual has to be checked by a person, which is why the review list above asks you to actually run it.

## Toolchain

`rust-toolchain.toml` in the repo root names the exact Rust version we use, currently 1.97.1. rustup reads it automatically and installs that version if you don't have it, so all four of us and CI are on the same compiler.

It's there because Rust older than 1.85 can't build this crate at all, since we use edition 2024, and the version in Ubuntu's apt is much older than that. The error you get is a confusing message about an unknown edition rather than something obvious like "your Rust is too old", so it's worth avoiding entirely.

It only works if you installed Rust with rustup. An apt install ignores it.

## GitHub settings worth turning on

Under Settings > Branches > Add branch ruleset for main:

- Require a pull request before merging
- Require approvals, set to 1
- Require status checks to pass, and pick the "Build and test" check
- Require branches to be up to date before merging

With those on, the Definition of Done is enforced by the repo instead of just being something we agreed to.
